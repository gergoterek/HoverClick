# Architecture

## Phase 0: Signed Menubar Shell

Create a stable, signed, menubar-only app bundle with a fixed bundle identifier and an Accessibility permission status check.

## Phase 1: Event Tap Permission Proof

Implemented a minimal listen-only `CGEventTap` proof for `kCGEventLeftMouseDown`. It validates Accessibility permission and event tap lifecycle behavior without changing click delivery, focusing windows, raising windows, or synthesizing events.

## Phase 2: Fast Click-To-Focus

Implemented fast click-to-focus behavior. The event tap now uses a pass-through default tap for `kCGEventLeftMouseDown` so HoverClick can attempt focus before returning the original event unchanged.

The callback remains pass-through: it never returns a replacement click event and never returns `NULL` for normal clicks. `NULL` is returned only for null event input; system tap-disabled pseudo-events return the received event after recovery handling. HoverClick does not synthesize clicks, move the cursor, move windows, or resize windows.

Event tap lifecycle guards:

- Installs only once and logs `click listener already installed; skipping duplicate install` when a duplicate install is requested.
- Logs `click listener paused by macOS reason=timeout` or `click listener paused by macOS reason=user input` for system-disabled pseudo-events.
- Checks Accessibility trust again inside the normal left/right mouse-down callback before entering AX hit-testing or focus logic. If permission is missing or revoked, the callback records permission-missing pass-through, schedules stale tap removal, performs no AX work, and returns the original event unchanged.
- Tracks user intent, tap object presence, CFMachPort validity, run loop source presence, run loop source validity, believed installed state, and believed enabled state separately.
- Re-enables the existing tap when the user still wants it enabled, the CFMachPort is valid, and the run loop source is valid, then logs `click listener resumed after ...`.
- Recreates the tap when disabled-event recovery finds a missing or invalid port/source, or when `CGEventTapEnable` does not leave the tap enabled.
- Removes the run loop source and CFMach port on app quit or menu disable.
- Logs `click listener remove requested but none active` for no-op cleanup.

For each click, HoverClick:

1. Reads the global click point from `CGEventGetLocation`.
2. Uses `AXUIElementCreateSystemWide` and `AXUIElementCopyElementAtPosition` to resolve the element under the cursor.
3. Reads the target pid and app name.
4. Reads the topmost CoreGraphics window under the point, skipping the Background Tab Hover card; Verbose Mode logs it for overlay diagnostics.
5. Uses AX hit-testing before treating a non-layer-0 CoreGraphics window as a hard skip.
6. Ignores HoverClick itself, menu roles, status items, protected menu-bar/system UI overlays, compact popup-style overlays, and unresolved targets.
7. Resolves a target window from `AXWindow` or by bounded `AXParent` climbing. If the target application is already frontmost, the click passes through as `already-frontmost` unless the clicked window sits behind another layer-0 window of the same application (commit `afc97b3`). A click on the application's own panel, palette or inspector under the cursor is not such a case and passes through. The window search stops at the first AX read that returns `kAXErrorCannotComplete` (`window search abandoned ... reason=ax-timeout`). A search or sibling test that times out passes the click through as `Window Search Timed Out` (`window search timed out stage=sibling-test|window-resolution`) instead of guessing `Already Frontmost` or `No Target Window`.
8. Focuses the window first and the application second (`-focusTargetApp:...`, `docs/DECISIONS.md` 2026-09-06). Every AX call carries a 200 ms messaging timeout (`HoverClickAXMessagingTimeoutSeconds`). HoverClick sets `kAXFocusedWindowAttribute` on the application element, performs `AXRaise` on the window, then sets `AXMain` and `AXFocused` on it. If any of these calls returns `kAXErrorCannotComplete`, the attempt is abandoned (`focus attempt abandoned reason=ax-timeout`), the application is not activated and the click passes through. `kAXFrontmostAttribute` is deliberately not set, because it brings the sibling windows of the same process forward as well (see the comment in `-focusTargetApp:...`).
9. Activates the application only under a condition (`docs/DECISIONS.md` 2026-09-14). If the clicked window is already the application's topmost window, the application is activated with `-activateWithOptions:NSApplicationActivateIgnoringOtherApps`. If it is not and `AXRaise` succeeded, the callback waits up to 60 ms (`HoverClickRaiseSettleTimeout`, `-waitForWindow:toBecomeFrontWindowOfPid:outWindowID:reached:`) for the window server to list the clicked window as the process's front window. Once it does, the process is activated with `SetFrontProcessWithOptions` and `kSetFrontProcessFrontWindowOnly` (`-activateFrontWindowOnlyOfPid:`, commit `afc97b3`, runtime measurement pending). The sibling windows stay where they were. Otherwise activation is skipped and the reason is logged as `skipReason=` on the `activation decision` line.
10. After a successful activation, runs two bounded waits that share a 150 ms cap (`HoverClickActivationWaitTimeout`): `-waitForWindowIDToReachFront:reachedFront:` and `-waitForFocusedElementOfApp:toBeInWindow:cap:reached:`. They are logged as `activation decision ... wait=` and `focus wait=...ms focusedElementInClickedWindow=`. Every wait is also capped by what is left of the 500 ms callback budget (`HoverClickCallbackBudgetSeconds`, `docs/DECISIONS.md` 2026-09-20).
11. Records frontmost-before, the activation return value, the AX operation results and the immediate verification from the window list and the AX focused application. For a click on a sibling window of the application that was already in front, the immediate verification passes only if the clicked window reached the front, because the application pid proves nothing there. A delayed verification diagnostic runs on the main queue 0.2 s after every attempt (`HoverClickDelayedVerificationDelay`); a success is counted once even when both verifications pass.
12. Returns the original event unchanged.

`observed leftMouseDown` from Phase 1 was only event observation. Phase 2 success requires target resolution plus a focus/raise action result.

Diagnostics intentionally remain detailed. Logs distinguish click receipt, AX element lookup, target pid/app/window resolution, ignored targets, `AXRaise`, app activation, immediate verification, delayed verification, event pass-through, tap creation, tap enable/disable, tap disabled/re-enabled/recreated recovery, and tap removal. Each click carries a monotonically increasing sequence id such as `click #42`.

`Diagnostics` > `Copy Summary` exposes the event tap lifecycle state needed for long-running failures: requested state, object/source presence, port/source validity, believed installed/enabled state, detected enabled state when available, last event tap callback type, last left/right mouse-down callback timestamps, and last recovery attempt/result. It also separates volatile last click handling from persistent background-focus diagnostics, including the last focus decision detail, the last right-click focus decision, the last background-focus attempt, trigger, target app, frontmost app before the attempt, activation return value, AX operation results, immediate frontmost app, delayed verification state, final result, failure reason, and last verified successful background focus. Later menu or overlay clicks may update the volatile last handled action, but they do not erase the stable last real/background click decision, recent non-menu mouse-down decision history, last focus decision detail, last right-click focus decision, last non-menu focus decision, last background-focus attempt, or last verified background-focus success. Overlay diagnostics record the last overlay/system UI skip reason, the topmost CoreGraphics owner/window/layer/title/bounds involved, the AX role/subrole/app seen at the click point, and the last eligible AX hit-test candidate when one is safely available. A narrow policy exception treats tiny untitled no-bundle high-layer Window Server surfaces near the click point as pass-through only when AX hit-testing resolves a normal non-menu app/window target underneath; this prevents cursor-like Window Server surfaces from blocking normal background focus while preserving actual menu/status/system UI skips. HoverClick must not ignore all Window Server windows globally, and this exception must not weaken real menu, status, popover, or system UI protection. The recent decision history keeps the latest 10 non-menu mouse-down decisions with sequence id, timestamp, trigger, click location, frontmost app before the click, topmost CG window summary, AX target summary, eligible-candidate state, policy decision or skip reason, overlay/system UI and compact-popup involvement, focus-attempt start, AX operation summary, immediate verification, delayed verification, and final result. Aggregate counters track mouse callbacks, left/right callbacks, non-menu decisions, focus attempts, successful verifications, policy skips, overlay/system UI skips, compact-popup skips, and HoverClick menu/status UI skips.

Delayed verification is diagnostic-only and runs 0.2 s after every focus attempt, whether the immediate verification passed or not. It is scheduled on the main queue after the original event has been left unmodified; it does not sleep in the event tap callback, consume the event, synthesize clicks, replay events, move the cursor, or add hover-assist-like work.

The callback itself does contain bounded polling waits before it returns the original event (steps 9 and 10 above), each with an exit condition and a cap. Per the user's reading recorded in `docs/DECISIONS.md` 2026-09-14 ("Invariant 6"), this is not delayed click delivery, because the event is neither held back nor posted.

## Chrome / Web Content Click-Through Diagnostics

The Google Docs missed-click investigation adds diagnostics only. The focus path still observes only left and right mouse-down events, resolves the AX target, optionally focuses the target app/window, and returns the original event unchanged.

Copied diagnostics now include a click-through investigation map that separates event tap health, callback observation, target detection, focus attempt, AX operation result, immediate and delayed verification, original-event pass-through, and app/web-content click handling. Recent non-menu decisions also record the source/frontmost app before the click, target bundle ID, whether the target is Chrome, target window title, already-frontmost state, explicit pass-through state, and a conservative browser/web-content note.

Chrome-specific diagnostics are limited to public app and AX information, primarily bundle ID `com.google.Chrome`, AX role/subrole/title, and window title. HoverClick may report a Google Docs or browser-web-content hint when those strings or roles are visible through AX, but these click diagnostics do not inspect Chrome internals, web pages, DOM state, editor state, pointer state, or hover state. Separately from the click path, Background Tab Hover (below) reads the pointer position on a timer and the title of a browser tab under it through Accessibility; it never reads page content or Chrome's own hover state.

When diagnostics show Chrome target detection, activation and AX operations attempted, immediate or delayed frontmost verification passed, and original-event pass-through, any remaining Google Docs missed click is outside HoverClick's direct observation and is likely app/web-content-level readiness or hover/click handling for the same physical mouse-down. This branch intentionally does not implement a workaround.

## Phase 3: Hover Focus Removal

The earlier optional Hover Focus experiment has been removed. HoverClick is not an AutoRaise-style app and must not focus, raise, or activate windows merely because the pointer moves over them.

The stable Phase 3 behavior is:

1. The event tap observes click-down triggers only: `kCGEventLeftMouseDown` and `kCGEventRightMouseDown`.
2. Mouse movement is never tapped. The only pointer reading is the Background Tab Hover position poll (see Background Tab Hover below), which shows a tab title and focuses nothing.
3. A left click may trigger the existing click-to-focus path when Left Click Focus is on.
4. A right click may trigger the same safe focus path only when Right Click Focus is on.
5. The original click event is returned unchanged.
6. No synthetic clicks, cursor movement, window movement, or window resizing are performed.

The old persisted Hover Focus defaults key is intentionally no longer read, so an existing saved setting cannot re-enable mouse-move-to-focus behavior.

## Stable And Experimental Paths

Stable Left Click Focus is the normal behavior and defaults ON. It focuses, raises, and activates a background window immediately before the original left-click event is delivered, then returns that original event unchanged.

Right Click Focus is an independent trigger and defaults OFF. It persists under `rightClickFocusEnabled`; when OFF, right-click events are returned unchanged without running the focus path, and copied diagnostics record that the right mouse down was observed but skipped because Right Click Focus was disabled. When ON, right-clicking a valid background window uses the same target-window filters, AX focused-window and `AXRaise` operations, conditional app activation and its bounded waits, immediate verification, and diagnostic delayed verification path as Left Click Focus, then returns the original right-click event unchanged so context menus remain normal. Copied diagnostics keep a right-click-specific decision line so manual tests can distinguish observation, target resolution, focus attempt, immediate or delayed verification, ineligible-target skips, and disabled-setting skips.

Finder context-menu follow-up handling is intentionally narrow. After a recent Finder right-click, if Finder is already frontmost when the next left-click arrives, HoverClick clears the short-lived Finder state and passes that left-click through before AX hit-testing, focusing, raising, or activation. This helps Finder context menus dismiss and lets Finder handle the follow-up click as natively as possible without synthetic click replay. HoverClick still does not force Finder actual selection; Finder may show a context-target highlight on right-click while keeping the previous actual selection.

The v0.9.0 updater-completion branch removes the visible no-op Hover Click Assist placeholder instead of implementing it. HoverClick still does not tap mouse movement, synthesize clicks, replay events, move the cursor, post replacement events, or schedule delayed assist behavior. Its only pointer reading is the Background Tab Hover position poll, which focuses nothing.

## OS Integration

Launch at Login is a menubar-only integration that uses `SMAppService.mainAppService` on macOS 13 and newer. It registers or unregisters the main app as the login item; no helper app is bundled, and the toggle does not change event tap, focus, updater, Accessibility, signing, or bundle identity behavior.

First-launch permission onboarding is native AppKit and Accessibility API integration only. When Accessibility is missing, HoverClick calls `AXIsProcessTrustedWithOptions` with `kAXTrustedCheckOptionPrompt` once for that launch, shows a native explanatory alert, leaves click detection inactive, and disables click-focus feature toggles until permission is granted. Non-prompting trust refresh runs on launch, when the app becomes active, and just before the status menu opens, so the menu and diagnostics follow permission changes without requiring an app restart. The explicit `Refresh Status` action remains the prompt-capable user action. The onboarding alert is retained as a non-modal alert and is closed automatically when a refresh sees Accessibility granted, avoiding stale permission-required UI and duplicate alert stacks. If Accessibility is revoked at runtime while a tap object still exists, the callback fails open before target resolution, returns normal mouse events unchanged, and the main queue removes the stale tap. `Accessibility Settings` remains an explicit user-click menu item; HoverClick does not open System Settings automatically during launch or validation.

Launch at Login onboarding is likewise explicit consent only. On macOS 13 and newer, if the main-app login item is not registered and the prompt has not already been shown, HoverClick asks whether to enable startup and stores that ask in the `launchAtLoginOnboardingPromptShown` user default. Registration happens only when the user chooses `Enable Launch at Login`; declining does not affect Accessibility permission or click-focus settings.

The status item uses a native template SF Symbol, `cursorarrow.click`, configured at 16 pt semibold/large scale inside a 23 pt `NSStatusItem`. The symbol remains vector-backed and template-tinted by AppKit for normal light/dark menu bar appearance. The branded app bundle icon is separate from the status item and is generated from `assets/HoverClickAppIcon-1024.png` into `Resources/HoverClick.icns`. The implementation avoids custom status windows, event monitors, or private menu bar APIs.

The status menu opens with the disabled `HoverClick` section header (`HoverClickCreateSectionHeaderMenuItem`). It is a custom view of `HoverClickSectionHeaderHeight` (18 pt) at indentation level 0 with one label in disabled text color, placed with the same leading and trailing insets as the menu rows; the `Access`, `Updates` and `Info` headers use the same geometry. The short version appears as a right-aligned `Version: <short-version>` label on the `Updates` section header (`HoverClickCreateUpdatesSectionHeaderMenuItem`). It reads `CFBundleShortVersionString` through `HoverClickDisplayVersion()`, with a generic fallback only for malformed bundle metadata. The build number is intentionally not shown in the menu rows or the Diagnostics submenu; bottom `About...` remains the single UI surface for the full version and build. The status-item tooltip uses stable, release-independent wording; section headers carry no tooltip.

Feature toggles use stable titles rather than appending `On` or `Off` to the title. The top-level menu is grouped with smaller subtle section headers: HoverClick, Access, Updates and Info, followed by a bottom separator with `About` above `Quit` with Cmd+Q. The HoverClick section contains Left Click Focus, Right Click Focus, Background Tab Hover, Bypass Key and Excluded Apps. Access contains a `Permissions` submenu with Accessibility status, Launch at Login, `Refresh Status`, and `Accessibility Settings`. Info contains `Guide`, `Help`, and `Diagnostics` submenus. Guide is the visible help fallback for native in-menu hover tooltips, which AppKit does not display on HoverClick's custom `NSView` menu rows (NSMenu's tracking loop never drives `NSView` tooltip display, and a custom `item.view` bypasses `NSMenuItem.toolTip`); it holds short word-wrapped explanations for Left Click Focus, Right Click Focus, Background Tab Hover, Bypass Key, Excluded Apps, Launch at Login, Permissions, Verbose Mode, and Copy Summary, built by `HoverClickCreateQuickHelpItem` as disabled informational rows (plain `NSView`, no tracking area/highlight/event loop, skipped by the highlight-reset pass) fixed to the menu content width so descriptions wrap instead of widening the menu. Help opens GitHub, Contact, Release Notes, and safe uninstall instructions; Diagnostics keeps `Copy Summary` and `Verbose Mode`; Updates keeps Sparkle's manual check and automatic-check toggle. The updater toggle writes through Sparkle's `automaticallyChecksForUpdates` setting, while `SUAutomaticallyUpdate` and `SUAllowsAutomaticUpdates` remain false so automatic download/install stays disabled. The Bypass Key and Excluded Apps submenu parents carry a native tooltip like the child status and action items; the Permissions, Guide, Help and Diagnostics parents do not. Non-closing in-menu rows for focus toggles, Background Tab Hover, permission refresh, Launch at Login, diagnostics copy, verbose diagnostics, and automatic update checks use small custom `NSView` rows backed by the original `NSMenuItem` sender/action, with SF Symbol images on the left and state indicators on the right. Custom header/control rows use named leading inset, icon spacing, and right accessory constants so section labels, left icons, title text, right-side indicators and the `Updates` header version share predictable visual columns anchored to the plain `About`/`Quit` rows. Other rows use normal `NSMenuItem.image` with SF Symbols where available instead of text icon prefixes or leading title padding, avoiding the previous `icon + space + label` appearance. `About` and `Quit` are plain native rows with no icons; `About` shows a small native informational alert with the current version, build, bundle identifier, and one-line description. GitHub, Contact, and Release Notes use explicit user-click link actions; Uninstall only shows instructions and deletes nothing. Native AppKit menus may still reserve a shared gutter, and HoverClick avoids fragile all-custom menu workarounds outside the rows that need non-closing behavior. Technical runtime details such as click detection state, updater state, and last handled action are not persistent diagnostic rows; they are available through `Diagnostics` > `Copy Summary`. Because native menu tooltips proved insufficient on custom rows, discoverability is provided by the static `Guide` submenu above rather than by custom tracking loops, focus-stealing help windows, hover timing controls or hover event monitors, none of which the menu uses. HoverClick installs no event monitor anywhere. Its one hover timing is the fixed dwell of Background Tab Hover, which has no user control and does not touch the menu.

Intentional shipped behavior or UI changes should bump `CFBundleShortVersionString` and/or `CFBundleVersion` consistently with the scope of the change. Git checkpoint-only tasks and read-only audits should not change version/build metadata. Docs-only tasks should not change version/build metadata unless they intentionally document a shipped version-label change.

The package does not attempt to customize the `.dmg` file's own pre-mount Finder icon. DMG Finder window background and icon layout are intentionally not part of the automated packaging architecture. They should remain future optional polish unless they can be produced deterministically without Finder UI automation, GUI scripting, browser automation, or fragile external dependencies.

Developer ID signing, notarization, stapling, a Mac App Store release, and a signed `.pkg` installer are not part of the current architecture. They remain optional future distribution work.

## Trigger Scope

HoverClick currently focuses windows only from configured click-down triggers. It does not add Scroll Focus because macOS already supports background scrolling in many apps.

Current menu controls expose:

- Left Click Focus
- Right Click Focus
- Background Tab Hover
- Bypass Key
- Excluded Apps
- Launch at Login
- Verbose Mode
- Auto Check Updates

The event tap should continue to observe only the current stable click inputs: `kCGEventLeftMouseDown` and `kCGEventRightMouseDown`.

Modifier Key Focus / Hold-to-Focus remains a future idea only. The failed 35 ms background drag assist / activation-settle experiment must not be reused; any future background click-and-drag work needs a new explicit, very risky branch, separate approval, and no synthetic clicks, event replay, cursor movement, or expanded event tap mask unless that risk is explicitly accepted.

Hover Click Assist is not part of the current product surface. The v0.9.0 updater-completion branch removes the default-off no-op placeholder from the menu and copied diagnostics. ## Excluded Apps

Excluded Apps adds a user-configurable Excluded Apps layer on top of the existing built-in Maccy bypass.

**Runtime bypass hierarchy:**
1. Modifier bypass (Shift / Fn): fires before AX target resolution; returns original event unchanged.
2. Built-in Maccy bypass (`isBuiltInCompatibilityBypassApplication:`): fires after AX target resolution; always active regardless of user list state; returns original event unchanged; sets `_lastBypassDecision = "bypassed-maccy"`.
3. User excluded apps (`userExcludedBundleIDs` consulted via `NSUserDefaults key "excludedAppBundleIDs"`): fires after built-in bypass check; sets `_lastBypassDecision = "excluded-app:<bundleID>"`.
4. Normal focus path: AX hit-test filtering, AX focused-window and `AXRaise` operations, conditional app activation and its bounded waits, verification (click path steps 5 to 11).

**Persistence:** `NSArray<NSString *>` in `NSUserDefaults`, key `excludedAppBundleIDs`. Empty strings and non-string entries are filtered at read time. Maccy's bundle ID is never stored in the user list; it is always covered by the built-in check.

**Menu:** The `Excluded Apps` submenu (HoverClick section, after Bypass Key, before the section separator) has two sections separated by a subsection header and optional separator. When Maccy is installed/resolvable an `Auto-added` section header appears first, followed by a non-interactive, non-removable row (`HoverClickCreateAutomaticEntryItem`) showing a `lock` SF Symbol icon on the left and the Maccy app name — no right-side accessory text, no tracking area; icon and title both rendered in `secondaryLabelColor` so the row reads as managed/locked but remains clearly readable. Then an `Added exclusions` section header, followed by user-added apps by friendly display name (each clickable to remove via `removeExcludedApp:`) sorted A–Z, or a disabled `No added exclusions` row when the user list is empty. A separator and `Add App Exclusion...` bottom the submenu. The built-in Maccy bypass is never persisted into `excludedAppBundleIDs`; it remains unconditionally active regardless of the visible row. Stored bundle IDs are resolved to friendly names with `displayNameForExcludedBundleID:` (via `NSWorkspace URLForApplicationWithBundleIdentifier:`), falling back to the raw bundle ID when the app is not installed. Section headers inside the submenu use `HoverClickCreateSubmenuSectionHeader` (width-aware, `secondaryLabelColor`) so they do not force the submenu wider than its calculated content width.

**App selector (`Add App Exclusion...`):** `chooseExcludedApp:` presents a dedicated app list selector — an `NSAlert` with an `NSPopUpButton` whose items are installed applications (display name + icon), sorted alphabetically and deduplicated by bundle ID. This is a list picker in the LinearMouse "Configure for" spirit, not a Finder/`NSOpenPanel` file browser. `installedApplicationsForSelector` enumerates apps from standard locations only — `/Applications`, `/Applications/Utilities`, `/System/Applications`, `/System/Applications/Utilities`, and `~/Applications` — with a shallow, non-recursive `NSFileManager contentsOfDirectoryAtPath:` scan (no full-disk scan, no deep recursion). For each `.app`: display name from `CFBundleDisplayName`/`CFBundleName`/file name, bundle ID from `NSBundle bundleWithURL:`, and icon from `NSWorkspace iconForFile:` (copied and sized to the menu image size). Apps without a bundle ID are skipped.

Selecting an app funnels its bundle ID into the shared `addExcludedBundleID:`, which trims whitespace, rejects missing IDs and duplicates, and treats the built-in Maccy bundle ID as already-handled (a friendly message, not an added entry), shown via `showInformationalAlertWithTitle:message:`. It then saves to `NSUserDefaults`, logs, and rebuilds the submenu. No app restart is required.

The earlier `NSOpenPanel`-based `Choose Application...`, the manual `Add by Bundle ID...` dialog, the `HoverClickEditableTextField` subclass, and the `panel:shouldEnableURL:` delegate were removed: the normal user path no longer requires browsing files or typing bundle IDs.

**Safety constraints (unchanged):** Event tap mask remains `kCGEventLeftMouseDown | kCGEventRightMouseDown` only. All bypass paths return the original event unchanged. NULL is never returned for normal user events. No synthetic clicks, event replay, delayed delivery, cursor movement, CGEventPost, or CGEventCreateMouseEvent in any new code path. The bounded waits inside the callback (click path steps 9 and 10) are not delayed delivery under the reading recorded in `docs/DECISIONS.md` 2026-09-14 ("Invariant 6").

## Background Hover

Since 2026-11-19 the feature covers every application: outside a browser's tab zones the named control, link or image under the pointer gets the same card (`HoverClickTabHoverReadElement`; `docs/DECISIONS.md`, 2026-11-19). The menu title is `Background Hover`; the text below describes the browser tab path, which is unchanged, under the feature's earlier name.

Chromium-based browsers register the mouse tracking area of their content view for the active application only. While another application is frontmost, a browser window therefore gets no mouse-moved or mouse-entered events: no tab hover card, no hover highlight and no expand-on-hover of a collapsed vertical tab strip. Background Tab Hover shows the title of the tab under a resting pointer in a small card of HoverClick's own, so keyboard focus never leaves the app the user is typing in.

**Setting:** `Background Tab Hover` in the HoverClick section, persisted under `backgroundTabHoverEnabled`; an absent key means ON. The feature runs only while the setting is on and Accessibility is trusted. It starts and stops with the same trust checks that drive the click listener and stops when the app quits.

**Pointer reading:** a main-thread `NSTimer` (0.1 s interval, 0.03 s tolerance, default run loop mode only) reads `+[NSEvent mouseLocation]` and `+[NSEvent pressedMouseButtons]`. No mouse movement is tapped and no event monitor is installed. The timer runs only while a supported browser (same predicate as the hit test) is running whose process is not the frontmost application; this is recomputed when the feature starts and when an application launches, terminates or becomes active. It also pauses while the screens sleep or the session is inactive; these observers are registered once, so the flags stay current while the feature is stopped. A pressed button hides the card, and nothing is tested for 0.35 s after a mouse-down. A hit test starts once the pointer has rested within 4 pt for 0.3 s; within 0.6 s of a card hidden for a hit-test answer the wait is skipped, so moving along a tab strip stays responsive. While a card is shown, leaving its tab starts a test at once: the card moves to the new tab or hides, and it hides when no answer arrives within 0.5 s. While the pointer stays on the card's tab, the tab is read again every 0.8 s, so a changed title updates the card and a closed tab hides it. At most one test is in flight, and a generation counter drops stale answers.

**Hit test:** it runs on a private serial queue and never on the main thread, because the click listener's run loop source is on the main run loop. The first normal-level (layer 0) on-screen window at the point decides. The card itself, fully transparent windows and the tiny untitled Window Server pointer surface are skipped. Windows above the normal level are passed over, because other applications keep click-through overlays there (measured 2026-11-17: Floaty at layer 3 over a whole Chrome window, Vorssaint at the shielding level over a whole screen) and the window list cannot tell such an overlay from a menu; a higher window of HoverClick itself (its menu) means no card and no Accessibility request to HoverClick's own process, and a higher window of the browser's own process (picture in picture) means no card either. The list is read once per hit test, and a probe point (see Gate) is used only where the list shows the same window: the top probe tries four points along the top band, the left probe moves right past a window that covers the leftmost column and ends at the pointer itself. What the pointer really reaches is settled by the Accessibility step below. The window must belong to an application that is not frontmost, the application's bundle identifier must start with `com.google.Chrome`, `org.chromium.Chromium`, `com.microsoft.edgemac`, `com.brave.Browser`, `com.vivaldi.Vivaldi` or `com.operasoftware.Opera` and must not continue with `.app.` (installed web app shims have no tabs), and the application must not be in Excluded Apps. The AX part is a hit test on the system-wide element, which follows event routing: it passes through click-through overlays and answers with the element the pointer really reaches. An answer from another process than the browser means the browser is covered there: no card, nothing learned, counted as `other app under pointer`. The system-wide element uses the process-wide 200 ms messaging timeout set at launch; every later read sets 150 ms on its element. Then a walk of at most 6 parents to an `AXRadioButton` with subrole `AXTabButton` (Chromium's tab), stopping at the window, the application, a web area or the `AXTabGroup` strip itself. Chrome answers a hit test over a vertical tab with an empty group laid over the whole strip (measured 2026-11-17), so a walk that ends on the strip goes on in two steps. First it checks that the strip belongs to the browser's own UI: the walk up from it must reach the window or the application before any web area, within 12 elements, because a page's own ARIA tab list is an `AXTabGroup` too. A strip inside a web area counts as page content. Then it searches the strip for the tab under the point: down through the groups, scroll areas, tab groups and lists whose frame holds the point, with 2 pt of slack for the gap between tabs; in a list of more than 12 children a binary search along the strip first, then a child-by-child pass when that misses, because Chrome lists tab views in creation order and a tab opened later can sit at the end of the list but in the middle of the strip. The search is bounded to 10 levels, 256 messages and 0.25 s; a search that runs out of messages or time ends without a card and is not counted as a timeout. Only the direct test searches; the probes below read the strip's frame only. Then one read of the tab's title or description, position and size. The strip's shape decides the orientation (taller than wide is vertical); without a strip, a tab more than 90 pt below the window top is vertical. A messaging timeout ends the test without a card and is counted.

**Gate:** AX hit tests are kept to the browser's own UI wherever the code can tell, because an AX request into a page may switch the browser's renderer accessibility on (inferred, not measured). The queue keeps a cache per window, keyed by window ID, at most 32 entries: the strip kind (unknown, vertical, horizontal or none), the right edge of a vertical strip, the time of the last check, the owning process and whether the top band answered with page content. An entry is dropped when the window size changes by more than 1 pt, and all entries of a browser are dropped when that browser becomes the active application, because its strip can only be collapsed, widened or turned horizontal while it is in front. With `dx` and `dy` the point's offset from the window's top left corner:

1. `dy` ≤ 60 pt, the browser UI band at the top (title bar, horizontal tabs, toolbar): the point is tested directly, unless this window's top band answered with page content (full screen, a popup, an undocked DevTools window) less than 30 s ago.
2. Inside a known vertical strip (`dx` ≤ strip edge + 4 pt): the point is tested directly. A direct test there that lands on page content forgets the strip, so it is learned again.
3. Otherwise, with `dx` ≤ 480 pt and a probe due (no entry, a vertical entry older than 2 s, any other entry older than 30 s): a window not known to have a vertical strip first gets a top probe at 160 pt, 16 pt from its top left corner; a horizontal strip there (one of its tabs, or the strip itself when the point misses the tabs) settles the kind and gives no card. Then a left probe 14 pt from the left edge at the point's height: a vertical tab or the vertical strip itself stores the strip's right edge, and the point is tested only when it lies inside the strip (the probe's own answer is reused when its tab holds the point). Without a vertical strip the kind becomes none. The probes land on page content only when the window shows no tab strip at the probe points (a popup; a full-screen window, whose top band is page content), at most once every 30 s per window.
4. Anything else gives no card.

A direct test that walks up to the strip refreshes the entry. Within 5 s of the last orientation check a direct test reuses the stored orientation instead of walking up again; it then only widens a vertical strip edge when the tab reaches further and leaves the check time alone, so the walk runs again after 5 s.

**Card:** a borderless non-activating `NSPanel` that cannot become key or main, ignores the mouse and joins all Spaces. It copies Chrome's own tab hover card as measured on a screenshot of Chrome 157 (2026-11-17): 257 pt wide with a 1 pt border and 8 pt corners, a 13 pt semibold title on at most two lines 20 pt apart, the first baseline 28 pt below the card's top, text 13 pt in from the edge, Chrome's dark or light card colours after the system appearance, and the tab under the pointer lit with a rounded 12.7 % white (6 % black in light mode) the way Chrome lights a hovered tab. The lit tab, the card and the card's shadow are drawn by one view in one transparent window, so one window number covers them all. A 12 pt site line sits 21 pt under the title, where Chrome shows the site's host. The tab's Accessibility element carries no URL (`AXURL` has no value), so `HoverClickTabHoverHostLookup` asks the browser on its own serial queue with two read-only Apple Events (`title of every tab of every window`, `URL of every tab of every window`; 27 to 34 ms for 253 tabs) and matches the answer to the hovered tab by title; two tabs with that title on different sites give no line. The hit test waits up to 0.15 s for the answer; a later answer lays the visible card out again. Answers are kept in memory for at most 30 s, asked again after 1 s, and never logged. macOS asks once per browser whether HoverClick may send these (`NSAppleEventsUsageDescription`); refused, the card shows the title alone and the request is repeated at most once a minute. It is placed on the screen under the pointer (else the screen holding the tab's centre, else the primary screen). For vertical tabs its left edge is on the tab's right edge and its top 1 pt above the tab's (left of the tab when the right side leaves the screen); for horizontal tabs it sits right below the tab; it never covers the tab. It appears with `orderFrontRegardless` and a 0.1 s fade, and HoverClick never becomes active. It hides on every left or right mouse-down (a constant-time step inside the click listener), whenever any application becomes active (the dwell then starts again, so the point is tested against the new frontmost application), on display changes, on screen sleep, when the session becomes inactive and whenever the timer stops. The click path skips the card's window number when it reads the topmost window under a click.

**Safety and privacy:** the event tap mask stays left and right mouse-down only, and the callback still returns the original event unchanged. Background Tab Hover only reads. No AX attribute is written, nothing is focused, raised or activated, no event is created, changed or posted and the cursor never moves. The log carries the start and stop lines with a reason and at most one verbose line a minute with the AX timeout count; tab titles and coordinates are never logged. `Diagnostics` > `Copy Summary` shows the setting and the counters: cards shown, hit tests started, hit tests that found a tab, hit tests where another application was under the pointer, AX timeouts and the slowest AX part.

**Runtime check:** `scripts/tab-hover-harness.sh` cuts this feature's block out of `HoverClick.mm`, swaps the pointer position and the frontmost application for its own, and runs the rest unchanged against the live windows: it rests on three reachable tabs per browser window and checks that the card shows that tab's title, follows, sits beside the strip and hides over the page. `--source` runs another copy of `HoverClick.mm` as a control. It moves no cursor and posts no event.
